# Agent Guide

This repository contains independent SIMD libraries for
[MoonBit](https://docs.moonbitlang.com). Follow these rules for source code,
documentation, tests, build configuration, and maintenance work.

## Workspace and module layout

- The repository root is a workspace described by `moon.work`, rather than a
  publishable umbrella module. Keep its member list explicit and up to date.
- Put module `justjavac/xxx` directly in the root directory `xxx/`. Its
  `moon.mod`, root `moon.pkg`, and implementation files belong in `xxx/`;
  avoid an additional `src/` directory or a shared `justjavac/simd` module.
- Each module must build, test, and publish independently. Declare dependencies
  in its own `moon.mod` and imports in the relevant `moon.pkg`; do not rely on
  workspace-only dependencies or sibling files outside the module.
- Use the current text formats `moon.mod`, `moon.pkg`, and `moon.work`.
- Organize packages by directory, as in `moonbitlang/core`. Add subpackages
  inside a module only when a real package boundary helps maintenance.
- Every module must contain `LICENSE`, a detailed `README.md`, a short
  `README.mbt.md`, an uppercase `BENCHMARK.md`, and a committed
  `pkg.generated.mbti` for each public package.

```text
moon.work
AGENTS.md
README.md
LICENSE
crc32/
  moon.mod                  # name = "justjavac/crc32"
  moon.pkg
  LICENSE
  README.md                 # Complete user and contributor guide
  README.mbt.md             # Small, executable introduction
  hasher.mbt
  scalar.mbt
  simd.mbt
  crc32_test.mbt             # Public API tests
  crc32_wbtest.mbt           # Internal implementation tests
  pkg.generated.mbti        # Generated by moon info
```

## Language, license, and documentation

- Write all project prose, comments, test names, identifiers, and metadata in
  English. Preserve exact external identifiers and author identities.
- License every module under MIT: set `license = "MIT"` in `moon.mod` and
  include the complete MIT license in that module's `LICENSE`. Preserve any
  required attribution when incorporating third-party source.
- Keep the root README detailed: explain the workspace, module catalog,
  supported systems and backends, development commands, coverage, and licensing.
- Keep each module's README detailed: describe the algorithm and its variant,
  installation and imports, public API, complete examples, mutation and state
  semantics, portability, performance limits, testing, and references.
- Keep `README.mbt.md` concise: a short description and one or two small
  `mbt check` examples using assertions. Maintain it and `README.md` as ordinary
  files so checkout works on Windows without symlinks.
- Public types, functions, methods, and traits require detailed doc comments.
  Explain purpose, parameters, return values, state changes, edge cases,
  failure conditions, and relevant algorithm or backend limits. Include checked
  examples for public operations when useful.
- Non-public declarations require a single-sentence doc comment explaining
  their responsibility. Use ordinary comments for non-obvious invariants or
  mathematical reasoning; do not narrate each statement.
- Point `moon.mod`'s `readme` at `README.md` and keep its description and
  repository URL accurate.

## Code readability and public API

- Prefer small, cohesive files, descriptive names, simple control flow, and a
  minimal public API. Keep algorithm selection separate from the public API.
- Separate top-level blocks with `///|`. Files organize code; they do not
  introduce namespaces. Moving blocks within a package must preserve semantics.
- Use methods for behavior belonging to a type, labeled parameters when they
  clarify a call, and views to avoid copying input buffers.
- Keep representation details private. Document mutable reference semantics
  and provide an explicit independent copy operation when callers need one.
- Use fixed-width unsigned arithmetic for checksums. State the polynomial,
  reflection, initial/final XOR, byte order, and continuation convention.
- Explain constants or generate tables from the algorithm; avoid unexplained
  numeric tables. Allocate reusable tables once, outside hot loops.
- Keep bounds and overflow reasoning visible. A vector load must be justified
  by a checked length or a matching bitstring pattern; never read beyond a view.
- Keep deprecated declarations in `deprecated.mbt` when they must be retained.
- Avoid unrelated refactors, speculative abstractions, and dependencies that
  merely replace a few straightforward lines.

## SIMD and portability

- Support Windows, Linux, and macOS. Keep commands, paths, line endings, and
  generated artifacts portable; avoid requiring a Unix shell for development.
- Support `native`, `wasm`, `wasm-gc`, and `js` unless a module's purpose makes
  a restriction unavoidable and its README explains it.
- Discover exact APIs with `moon ide doc` and inspect installed core sources
  before using intrinsics. The former `moonbitlang/core/v128` package was renamed
  to `moonbitlang/core/simd`; use the maintained API and the built-in `V128`
  type on toolchains that provide it.
- Allow experimental SIMD imports explicitly in `moon.pkg`. Specify the
  toolchain version or channel in CI and record the validated compiler version;
  pin a release when the download service provides an immutable release.
- Isolate SIMD code with backend conditions where appropriate and provide a
  scalar implementation with identical public behavior on other backends.
- Do not assume x86, ARM, host endianness, alignment, or optional CPU features.
  Architecture-specific acceleration needs a safe fallback and feature checks.
- Test scalar and SIMD implementations against an independent checksum oracle,
  including empty input, short tails, block boundaries, nonzero initial states,
  unaligned subviews, and different streaming chunk sizes.
- Benchmark meaningful short and large inputs before claiming a speedup.
  Report the backend and hardware; do not equate portable vector operations
  with hardware CRC or carry-less multiplication instructions.
- Keep measured performance in each module's `BENCHMARK.md`, with its complete
  `BENCHMARK-DATA.json` snapshot. Record the source commit, CI run and attempt,
  OS, runner image, CPU, architecture, toolchain, commands, input sizes,
  view offsets, sample counts, latency, throughput, and variability.
- Generate benchmark reports from one complete CI run. Preserve raw logs as
  artifacts and commit a selected snapshot deliberately; keep local measurements
  clearly separate from CI results.

## Tests, CI, and coverage

- Prefer black-box `*_test.mbt` tests through the public package alias. Use
  `*_wbtest.mbt` for private algorithms and implementation parity checks.
- Use `assert_eq` and `assert_true` for exact numerical results. For structured
  snapshots, derive `Debug` and use `debug_inspect`; update snapshots only for
  intentional behavior changes.
- Cover reference vectors, independent differential checks, continuation,
  resets, copying, and concatenation/combine laws where relevant.
- Run native tests with coverage on Windows, Linux, and macOS in GitHub Actions.
  Exercise the other supported backends in CI as well.
- Produce a filtered Cobertura report for each module on each OS. Upload only
  those reports to Codecov, using the `linux`, `macos`, and `windows` flags and
  `disable_search: true` to exclude dependency and sidecar reports.
- Maintain total, Linux, macOS, and Windows coverage badges in the root README.
  Keep URLs aligned with the repository and default branch. Configure Codecov
  to aggregate all expected OS uploads before reporting status.
- Measure coverage and address meaningful gaps; do not skip executable code to
  inflate the result or impose a 100% gate without an explicit requirement.
- Ignore build directories, fetched dependencies, and coverage artifacts.

## Development workflow

1. Inspect `moon.work`, the affected module's `moon.mod`, and its `moon.pkg`.
   Check existing changes before editing.
2. Discover APIs with `moon ide doc`; use `outline`, `peek-def`, and
   `find-references` for semantic navigation.
3. Make a focused change and add public API tests, checked documentation
   examples, and differential tests for algorithm changes.
4. Run `moon check --target all --deny-warn` and `moon test --target all` from
   the workspace, or use `moon -C xxx ...` for the affected module.
5. Run `moon test --target native --enable-coverage`, then
   `moon coverage analyze -p justjavac/xxx -- -f cobertura -o coverage.xml`.
   Inspect the report and use the same command in CI.
6. Finish with `moon info` followed by `moon fmt`. Review generated `.mbti`
   changes as public API changes, and rerun affected checks if needed.
   Never edit `.mbti` files manually.
7. Summarize behavior changes, validation, actual coverage, and any platform
   checks that still require CI. Do not claim checks ran on an unavailable OS.

When adding a workspace member, update the module catalog and CI coverage
report commands so each OS upload includes the new module's filtered report.
Add its benchmark collection command and compatible named result inventory
to the Benchmarks workflow and report generator as well.

Use `.mbtx` for project automation that needs loops, parsing, transformation,
or process orchestration. Keep CI commands direct where possible and launch
MoonBit scripts for shared automation instead of duplicating shell scripts.

## Git and GitHub identity routing

Before an authenticated GitHub operation, run `git rev-parse --show-toplevel`.
Compare the root case-insensitively, accepting both slash styles:

- Under `D:\jianchang56` (including that directory itself), select
  `jianchang56` with
  `gh auth switch --hostname github.com --user jianchang56`; verify
  `gh api user --jq .login` returns `jianchang56`. The expected commit author is
  `舰伥 <jianchang_56@qq.com>`.
- In every other repository, select `justjavac` with
  `gh auth switch --hostname github.com --user justjavac`; verify
  `gh api user --jq .login` returns `justjavac`. The expected commit author is
  `迷渡 <justjavac@gmail.com>`.

Apply this routing to `git fetch`, `pull`, and `push`, creating or changing
remotes, and all `gh` account, repository, PR, issue, release, comment, and
workflow operations. Stop remote operations if switching or verification fails.
Git commit identity remains controlled by the existing `includeIf` configuration
and global hooks; do not change identity settings or print authentication tokens.
